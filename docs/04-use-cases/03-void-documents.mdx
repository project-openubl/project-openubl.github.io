Para anular un comprobante que la SUNAT ya aceptó envías una **comunicación de baja**: un documento que lista los comprobantes que quieres dar de baja y el motivo de cada uno. Las percepciones y retenciones se anulan de la misma forma, con un **resumen de reversiones**.

A diferencia de una factura, estos documentos se procesan de forma **asíncrona**: al enviarlos, la SUNAT no responde con el CDR sino con un **ticket**. Luego consultas ese ticket para obtener el resultado.

## Comunicación de baja

Cada comprobante se indica con su serie y su número **por separado** (`F001` y `1`, no `F001-1`). El identificador del documento, `RA-AAAAMMDD-N`, se calcula a partir de la fecha de emisión de la baja y del correlativo (`numero`) que indicas; no lo escribas a mano.

Valores que se completan solos:

- **Fecha de emisión** de la baja (`fechaEmision` / `fecha_emision` / `FechaEmision`): hoy en Perú.
- **Tipo de cada comprobante**: se deduce del prefijo de la serie: `F` → `01` (factura), `B` → `03` (boleta), `P` → `40` (percepción), `R` → `20` (retención), `T` → `09` y `V` → `31` (guías).

:::note Plazos de la SUNAT

La SUNAT solo acepta la baja dentro de un plazo contado desde la emisión del comprobante. xhandler no controla ese plazo: si usas fechas antiguas, la SUNAT puede rechazar la baja.

:::

## Enviar y consultar el ticket

Firma la baja y envíala con `FileSender`, igual que cualquier otro documento. xhandler reconoce que es una baja y usa el servicio de resúmenes de la SUNAT (`sendSummary`), que responde con un ticket. Después consulta el ticket hasta que deje de estar **en proceso** (código `98`).

La consulta recibe el **mismo XML firmado** que enviaste: xhandler lo usa para saber a qué servicio de la SUNAT preguntar.

<Tabs groupId="lang" queryString>
<TabItem value="java" label="Java">

```java
SigningKey key = SigningKey.fromPkcs12(Files.readAllBytes(Path.of("certificado.pfx")), "password");
byte[] signed = new XSigner().sign(xml.getBytes(StandardCharsets.UTF_8), key);

FileSender sender = new FileSender(
        URLs.beta(),
        Credentials.builder()
                .username("12345678959MODDATOS")
                .password("MODDATOS")
                .build()
);

// 1. Enviar: la SUNAT responde con un ticket
SunatResponse sent = sender.sendFile(signed);
if (!sent.isTicket()) {
    throw new IllegalStateException(sent.getStatus() + " " + sent.getMetadata().getDescription());
}
String ticket = sent.getSunat().getTicket(); // guárdalo

// 2. Consultar el ticket
SunatResponse result = sender.verifyFileTicket(signed, ticket);
while (result.getStatus() == Status.EN_PROCESO) {
    Thread.sleep(5_000);
    result = sender.verifyFileTicket(signed, ticket);
}

// ACEPTADO La Comunicacion de baja RA-..., ha sido aceptada
System.out.println(result.getStatus() + " " + result.getMetadata().getDescription());
```

```rust
let signed = UblFile::from_bytes(XSigner { xml_document: xml }.sign(&key)?)?;

// 1. Enviar: la SUNAT responde con un ticket
let ticket = match sender.send_file(&signed).await?.response {
    SendFileAggregatedResponse::Ticket(ticket) => ticket, // guárdalo
    SendFileAggregatedResponse::Fault(fault) => anyhow::bail!("{} {}", fault.code, fault.message),
    SendFileAggregatedResponse::Cdr(_, cdr) => anyhow::bail!("CDR inesperado: {}", cdr.description),
};

// 2. Consultar el ticket
loop {
    match sender.verify_file_ticket(&signed, &ticket).await?.response {
        VerifyTicketAggregatedResponse::NoCdr { status_code }
            if Status::from_code_str(&status_code) == Status::InProgress =>
        {
            tokio::time::sleep(std::time::Duration::from_secs(5)).await;
        }
        VerifyTicketAggregatedResponse::Cdr(_, cdr) => {
            // ACEPTADO La Comunicacion de baja RA-..., ha sido aceptada
            println!("{} {}", cdr.status(), cdr.description);
            break;
        }
        VerifyTicketAggregatedResponse::NoCdr { status_code } => {
            println!("sin CDR, código {status_code}");
            break;
        }
        VerifyTicketAggregatedResponse::Fault(fault) => {
            println!("{} {}", fault.code, fault.message);
            break;
        }
    }
}
```

```go
pfx, err := os.ReadFile("certificado.pfx")
if err != nil {

	return err

	// ACEPTADO La Comunicacion de baja RA-..., ha sido aceptada

case verify.Fault != nil:
	fmt.Println(verify.Fault.Code, verify.Fault.Message)
```

La consulta del ticket devuelve uno de tres resultados:

- **CDR**: la SUNAT terminó de procesar la baja; el CDR indica si fue aceptada o rechazada.
- **Sin CDR**: todavía no hay respuesta. El código `98` significa que sigue en proceso; vuelve a consultar más tarde.
- **Error de la SUNAT** (fault): por ejemplo, un ticket que no existe.

xhandler no consulta el ticket automáticamente: el bucle y el tiempo de espera de los ejemplos son tuyos. En una aplicación real **guarda el ticket** junto al documento, porque la consulta puede hacerse minutos u horas después, incluso desde otro proceso.

### Consultar solo con el ticket

Si no conservas el XML firmado, guarda también el **destino** del ticket que devuelve el envío y consulta con él. En Rust y Python es `verify_ticket_target` en el resultado del envío, que se pasa a `verify_ticket(target, ticket)`; en Go es `result.VerifyTicketTarget` (un puntero), que se pasa como `VerifyTicket(ctx, *result.VerifyTicketTarget, ticket)`.

En Java la respuesta del envío no incluye el destino, así que lo más simple es conservar el XML firmado y usar `verifyFileTicket`, que lo acepta como `byte[]` o como `Path`.

:::caution Consultas en el entorno beta

El entorno beta de la SUNAT no siempre procesa los tickets de forma confiable. Si la consulta en beta se queda en proceso o falla, no significa necesariamente que tu código esté mal.

:::

## Resumen de reversiones (percepciones y retenciones)

Las percepciones y retenciones no se dan de baja con una comunicación de baja sino con un **resumen de reversiones**. Tiene los mismos campos (y usa los mismos ítems, `VoidedDocumentsItem`), pero su identificador es **`RR-AAAAMMDD-N`**.

El envío y la consulta del ticket son **idénticos** a los de la comunicación de baja. Como las líneas son percepciones (`40`) o retenciones (`20`), xhandler envía el documento y consulta el ticket en el servicio de percepciones y retenciones de la SUNAT (`perceptionRetention` / `perception_retention` / `PerceptionRetention` en las URLs). No mezcles en un mismo resumen de reversiones líneas de percepciones o retenciones con facturas o boletas: el servicio se elige según el tipo de la primera línea.

:::note El identificador es RR, no RA

El comentario del campo `documentoId` / `documento_id` / `DocumentoId` de `Reversion` dice `RA-AAAAMMDD-N` en Java, Python y Go. Es un error de documentación: el identificador que se genera es `RR-AAAAMMDD-N`.

:::

## Diferencias entre lenguajes

- **Rust**: `Reversion` es una *tuple struct* que envuelve un `VoidedDocuments`; accede a sus campos con `reversion.0`. El resultado del envío trae el ticket en la variante `SendFileAggregatedResponse::Ticket`.
- **Java**: comprueba `sent.isTicket()` antes de leer el ticket con `sent.getSunat().getTicket()`. `verifyFileTicket` lanza una excepción si le pasas un XML que no se procesa con ticket (por ejemplo, una factura).
- **Python y Go**: el resultado del envío trae exactamente uno de `cdr`, `ticket` o `fault` (`CDR`, `Ticket`, `Fault` en Go).
